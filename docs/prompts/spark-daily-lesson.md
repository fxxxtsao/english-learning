# Gemini Spark 每日教材生成提示詞

**用途**：貼進 Gemini Spark 建立每日排程任務，每天從試算表既有的教材素材中挑一份出題。

**Spark 不再負責抓取教材**。三次實測證明它到不了來源網站（VOA 的 Akamai 回它 403、BBC 封鎖 Google 的 AI 爬蟲），也寫不動長文字欄位。抓取改由本機的 `tools/fetch-materials.js` 負責，抓完用 `tools/upload-materials.js` 寫進 lessons 分頁成為「素材列」（`lesson_id` 為空的列）。Spark 每天挑一列素材填上題目，它就成為一堂課。

**前置需求**
- Google AI Pro 或 Ultra 訂閱（Spark 的使用條件）
- 一份名為「English Learning」的 Google 試算表，含 `lessons` 與 `settings` 兩個分頁，欄位定義見 `docs/specs/2026-09-02-content-pipeline.md`
- 排程設定：每日早上執行一次

## 提示詞本文

```
每天從我的 Google 試算表「English Learning」挑一份教材出題。
你不需要上網，所有內容都已經放在試算表裡了。

步驟：

1. 讀取 settings 分頁 B1 儲存格的 current_level（CEFR 等級，例如 B1、B2）。

2. 讀取 lessons 分頁，找出「A 欄 lesson_id 是空的」那些列。
   這些是已經備好原文與音檔、但還沒出題的教材。
   從中挑一列，優先選 B 欄 level 最接近 current_level 的。
   記下它是第幾列。

3. 讀取你挑中那一列的這三個欄位：
   - E 欄 title：標題
   - F 欄 reading_text：文章全文
   - K 欄 transcript：音檔前三分鐘的逐字稿

4. 根據讀到的內容產生三樣東西，全部用英文，只有單字的中文釋義用繁體中文：

   - reading_questions：針對 F 欄全文出 4 題四選一，
     其中 2 題問細節、1 題問主旨、1 題需要推論。
     JSON 陣列，每題結構為
     {"prompt":"題目","options":["A","B","C","D"],"answer_index":0,"explanation":"為什麼選這個，繁體中文"}

   - listening_questions：針對 K 欄逐字稿出 3 題四選一，格式同上。
     只能問 K 欄逐字稿裡出現過的內容，
     不要問到 F 欄後半段、逐字稿沒涵蓋到的部分——
     那段音檔使用者不會聽到，問了會變成無解題。

   - vocab：從 F 欄全文挑 8 到 12 個難度在 current_level 以上的字詞。
     JSON 陣列，每個結構為
     {"term":"字詞","pos":"詞性","definition_en":"英文釋義","definition_zh":"繁體中文釋義","example":"直接取自 F 欄原文的句子"}
     每個 term 都必須真的出現在 F 欄原文裡，不可自行造字。

5. 把結果寫回**你挑中的那一列**，不要新增列。
   只填下面這五個欄位，其他欄位一律不要動：

   - A 欄 lesson_id：今天的日期，格式 YYYY-MM-DD，以純文字寫入，
     不要讓試算表把它轉成日期格式
   - G 欄 reading_questions：壓縮成單行的 JSON 字串
   - L 欄 listening_questions：壓縮成單行的 JSON 字串
   - M 欄 vocab：壓縮成單行的 JSON 字串
   - N 欄 generated_at：現在時間

6. 完成後告訴我你寫在第幾列、以及那篇文章的標題。

7. 如果找不到任何 A 欄為空的列，表示教材存量用完了。
   這種情況不要寫入任何資料，改寄一封 email 通知我需要補充教材。
```

## 設計理由

**第 1 步讀 `current_level` 而非寫死難度**：難度由網頁端依答對率回寫，Spark 每天讀最新值。這條路徑斷掉的話難度會永遠停在初始值。

**第 6 步寧可不產出也不寫半筆**：缺欄位的列在網頁端表現為「程式壞掉」，使用者無從分辨是內容缺漏還是程式錯誤，除錯成本遠高於少一天內容。

**單字要求「必須出現在原文中」**：語言模型會憑空造出看似合理的例句與詞條，這條限制配合驗證器的比對檢查可以攔下來。

**Spark 只寫五個短欄位，一個長文字都不碰**：三次實測畫出了它能力的邊界——短欄位（含題目與單字的 JSON）全部寫入成功，兩個長文字欄位（`reading_text`、`transcript`）每次都被放掉。新分工把長文字全部交給本機腳本預先填好，Spark 只填 `lesson_id`、三個 JSON 欄位與 `generated_at`，正好落在它做得到的範圍內。

**音檔區段固定為 0 到 180 秒，由腳本預填**：VOA 的音檔就是文章的朗讀，從頭開始必然落在句子邊界，不需要聽過音檔才能決定切點。逐字稿取原文開頭、切到句尾，長度約當 180 秒的朗讀量（以每分鐘 110 字估算）。這讓 Spark 連「決定音檔區段」都不必做。

**聽力題限定只能問逐字稿涵蓋的內容**：使用者只會聽到前三分鐘，若題目問到後半段，會變成聽再多次也答不出來的無解題。

**音檔網址一律取自文章頁，不從 podcast feed 抓**：podcast feed 指向的是音檔片段頁（`page_type` 為 `clipsexternal`），只有音檔沒有文字；真正的文章頁（`/a/<標題>/<編號>.html`，`page_type` 為 `article`）兩者兼具。這個差異一度讓抓取拿到有音檔卻沒有內文的頁面。：VOA 文章頁的播放器是動態腳本載入的，模型讀 HTML 讀不到 MP3 網址——首次實跑就卡在這一步。RSS 是為機器讀取而設計的格式，音檔網址是規格明定的欄位，穩定得多。附帶好處是 feed 的項目連結天然對應到該篇文章頁，音檔與逐字稿的配對不會錯位。

**取消「最近七天內發布」**：VOA 已停更，這個條件會讓每天的搜尋必然落空。改為「從存量中挑未用過的」之後，光三個分類 feed 就有約 600 則，接近兩年份的每日教材。對語言學習而言，文章是去年或今年寫的並不影響練習價值，供應穩定才影響。

**寫入拆成兩步**：合併成一次寫入時，模型會完成所有生成工作卻獨獨放掉最長的兩個欄位（實測結果）。拆開之後它沒有可以省略的餘地，而要求回報字元數則是為了讓「被截斷」跟「寫成功」區分得出來——這兩者在試算表上看起來一模一樣。
