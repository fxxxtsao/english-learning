# 英文練習內容每日生成管線

## 問題陳述

使用者要在通勤與工作空檔用手機練英文閱讀與聽力，需要穩定供應難度貼合自己程度、附題目與解說、附音檔的材料。

這類自學計畫最常見的失敗點不是內容品質，是**供應中斷**——手動找材料的流程會在幾週內斷掉。因此本管線的首要設計目標是「不需要使用者記得做任何事」，其次才是內容品質。

管線每日自動執行，由 Gemini Spark 負責文字部分、Google Apps Script 負責音檔部分，產物落在 Google Sheets 與 Google Drive。使用者不需開電腦。

## 資料來源

| 來源 | 取得方式 | 更新頻率 | 權限/憑證 | 已知限制 |
|---|---|---|---|---|
| VOA Learning English | Spark 瀏覽 `https://learningenglish.voanews.com/` | 每日 | 公開，無需憑證 | 主力來源。美國政府作品屬公眾領域，散布限制最少。內容分三級 |
| BBC Learning English | Spark 瀏覽 `https://www.bbc.co.uk/learningenglish/` | 每週 | 公開，無需憑證 | 備用來源。對話感較強。著作權屬 BBC，僅供個人學習，不得公開再散布 |
| Gemini Spark | 每日排程任務，執行使用者設定的提示詞 | 每日 | 需 Google AI Pro / Ultra 訂閱（使用者已有） | 不可下載檔案至 Drive；產出為自然語言模型輸出，JSON 格式不保證合法；同一提示詞每次執行結果不同 |
| Google Apps Script | 每日時間觸發器，`UrlFetchApp` 下載 MP3 | 每日 | 使用者的 Google 帳號 | 單次執行上限 6 分鐘；`UrlFetchApp` 單檔上限 50MB；每日觸發器執行時間有配額 |

**首次設定時必須實測來源可用性**：確認上述兩個網站仍能找到「逐字稿與音檔同頁」的內容。網站改版是本管線最可能失效的地方，且失效時 Spark 會安靜地找不到東西——這是為什麼提示詞要求失敗時寄信通知。

## 資料契約

產物存放於 Google 試算表「English Learning」，兩個分頁。

**分頁 `lessons`** — 一列 = 一課 = 一天份

| 欄 | 欄位 | 型別 | 說明 |
|---|---|---|---|
| A | `lesson_id` | string | `YYYY-MM-DD`，即產出當日日期，全域唯一 |
| B | `level` | string | CEFR，A1-C2，該篇實際難度 |
| C | `source` | string | `voa_le` / `bbc_le` |
| D | `source_url` | string | 原始頁面網址，去重用的唯一鍵 |
| E | `title` | string | |
| F | `reading_text` | string | 純文字全文，不含網頁排版 |
| G | `reading_questions` | JSON string | 4 題，見下方題目結構 |
| H | `audio_url` | string | 來源站的 MP3 直連 |
| I | `audio_start_sec` | int | 練習區段起點，落在句子邊界 |
| J | `audio_end_sec` | int | 練習區段終點，區段長度 120-180 秒 |
| K | `transcript` | string | 上述區段對應的逐字稿 |
| L | `listening_questions` | JSON string | 3 題 |
| M | `vocab` | JSON string | 8-12 個 |
| N | `generated_at` | ISO8601 | Spark 寫入時間 |
| O | `audio_file_id` | string | Apps Script 存入 Drive 後回填的檔案 ID。空值代表音檔尚未抓取或抓取失敗 |

**分頁 `settings`** — 單列設定

`A1 = current_level`（標題），`B1 = <CEFR 值>`。這是 Spark 每日選材的難度依據，由網頁端依使用者答對率回寫（見網頁 spec）。這條回寫路徑是難度自適應機制的閉環，斷了難度就會永遠卡在初始值。

**題目結構**（`reading_questions` / `listening_questions` 內的元素）

`{"prompt": string, "options": [4 個 string], "answer_index": 0-3, "explanation": string（繁體中文）}`

**單字結構**（`vocab` 內的元素）

`{"term": string, "pos": string, "definition_en": string, "definition_zh": string（繁體中文）, "example": string（取自本篇原文）}`

**主鍵與粒度**：一列代表一天份的一課，主鍵 `lesson_id`。`source_url` 為去重鍵，不得重複出現。時間一律 ISO8601 UTC。

空值語意需區分：`audio_file_id` 為空是**正常的暫時狀態**（Spark 先寫列，Apps Script 稍後回填）；其餘欄位為空代表**該列損壞**，網頁端應跳過該課並回報。

## 轉換決策

**難度口徑用 CEFR，不用多益分數。** 來源本身即用 CEFR 或可直接映射；多益是考試分數而非材料難度，混用會讓難度調整失去意義。使用者未考過檢定，起始難度設 B1，之後由答對率驅動。

**音檔不裁切，改存原檔加起訖秒數。** Spark 無法處理音訊，Apps Script 也沒有音訊剪輯能力。改由網頁播放時以 `audio_start_sec` / `audio_end_sec` 限制播放範圍。這個決策同時省掉整個音訊處理環節，是本次改為 Google 生態自動化後最划算的簡化。

**音檔由 Apps Script 下載至 Google Drive**，每日於 Spark 排程後一小時執行，掃描 `lessons` 中 `audio_file_id` 為空的列、下載對應 MP3、回填檔案 ID。分開執行是因為 Spark 完成時間不固定，串接會有競態。

Drive 只保留最近 8 週音檔（約 40 個檔案），更舊的自動刪除。舊課的文字內容永久保留在 Sheets，只是不再能播音。

**去重以 `source_url` 為唯一鍵**，Spark 在選材前先讀取既有列排除。

**失敗時不寫入不完整的列。** Spark 若任一步失敗（找不到合適文章、無逐字稿、無音檔），改為寄信通知使用者並跳過當日。理由：一列缺欄位的資料在網頁端會表現為「程式壞掉」，使用者無從判斷是內容缺漏還是程式錯誤，除錯成本遠高於少一天內容。

**Spark 產出的 JSON 字串不保證合法。** 這是使用語言模型直接寫入結構化資料的固有風險。因應方式是驗證器（見測試決策）每日掃描，把壞列標記出來，而非假設它一定正確。

## 驗收查詢

本管線為全新建置，無現況可量測。標記「首次執行後回填」者，必須在實際跑過後把實測值寫回本文件，不得先填猜測值。

- [ ] **每日產出列數**：`lessons` 分頁每日新增列數 → 期望 = 1，允許 0（來源無合適內容，且應同時收到通知信）。> 1 為異常，代表排程重複觸發
- [ ] **連續供應率**：最近 30 天中有內容的天數 → 首次執行滿 30 天後回填基準線。低於 20 天代表來源或排程有系統性問題
- [ ] **去重**：`source_url` 的重複組數 → 期望 = 0，零容忍
- [ ] **必填欄位完整性**：除 `audio_file_id` 外所有欄位的空值率 → 期望 = 0
- [ ] **JSON 可解析率**：`reading_questions`、`listening_questions`、`vocab` 三欄能成功解析為合法 JSON 的比率 → 期望 = 100%，實測值首次執行後回填。這是 Spark 方案最可能出問題的一項
- [ ] **題目結構**：閱讀恰 4 題、聽力恰 3 題，每題恰 4 選項、`answer_index` 落在 0-3
- [ ] **單字出處**：每課 8-12 個單字，且每個 `term` 能在該列 `reading_text` 或 `transcript` 中以原形或變化形找到 → 期望符合率 = 100%。這一項專門抓語言模型憑空造字
- [ ] **音檔區段長度**：`audio_end_sec - audio_start_sec` 落在 120-180 秒
- [ ] **音檔回填率**：Spark 寫入滿 24 小時的列中，`audio_file_id` 非空的比率 → 期望 = 100%，實測值首次執行後回填
- [ ] **音檔可播放**：抽查 Drive 中的檔案能正常播放，且 `audio_end_sec` 未超出檔案實際長度
- [ ] **人工抽樣**：每週抽 1 課，人工確認題目確有唯一正解、解說正確、中文釋義無誤

## 可重現性

**本管線不可重現，這是採用 Spark 的已知代價。** 同一天跑兩次會挑到不同文章、產出不同題目，且無 seed 可固定。

因應方式是**保存而非重現**：`lessons` 分頁為 append-only，產出過的內容永久保留，不覆蓋、不重算。需要回溯某一天練了什麼，查該列即可；不嘗試重跑得到同一份輸出。

Spark 的提示詞本身納入版控（存於本專案 `docs/prompts/`），提示詞改動需記錄日期，這樣才能解釋「為什麼某段期間的題目風格不同」。

參數（目標難度、單字數量、音檔區段長度）寫在提示詞裡，不另設定檔——Spark 讀的就是提示詞，多一層設定檔只會讓兩邊不同步。唯一例外是 `current_level`，因為它需要被網頁端回寫。

## 測試決策

**Seam（已與使用者確認）**：測試放在資料進入網頁之前的解析與驗證層，不測 Spark 本身。

| Seam | 簽章 | 要驗什麼 |
|---|---|---|
| 列解析 | `parseLessonRow(row) -> {lesson \| null, errors[]}` | Sheets 原始列轉為 lesson 物件。重點是**壞資料不會讓整批爆掉**：JSON 解析失敗、欄位缺漏、`answer_index` 超出範圍時回傳具名錯誤而非拋例外 |
| 內容驗證 | `validateLesson(lesson) -> errors[]` | 上述驗收查詢中可程式化的項目。與網頁端共用同一支 |

驗證器需能對整份 `lessons` 分頁批次重跑，作為每日健檢——這是唯一能及早發現 Spark 產出品質漂移的機制。

**Spark 的執行與網站抓取不寫自動測試。** 它是外部黑箱服務，測試必然間歇性失敗。改以「失敗寄信」與每日驗證器掃描取代。

**Apps Script 的音檔下載不寫單元測試**，改為執行期檢查：下載後確認檔案大小 > 0、MIME type 為音訊，失敗則保留 `audio_file_id` 為空並記錄原因，隔日重試。

**Fixture 用真實的 Sheets 列存成固定檔案**，需刻意包含幾筆壞資料（JSON 少一個括號、選項只有 3 個、單字不在原文中）。合成的完美資料測不出這支解析器真正要擋的東西。

## 不在範圍

- **語音辨識產逐字稿**：只接已附逐字稿的來源。使用者已選擇「先用學習材料，能聽懂了再換真實材料」
- **真實新聞 / 商業 Podcast**：第二階段。這些來源多半無現成逐字稿
- **音訊裁切**：改用起訖秒數，見轉換決策
- **寫作與口說材料**：使用者已明確決定擺到第二階段
- **內容公開再散布**：僅供本人學習，網站不對外開放
- **Claude Code 手動批次**：已被 Spark 每日自動取代。若 Spark 方案實測不可行再回頭考慮
