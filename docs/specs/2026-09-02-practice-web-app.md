# 英文練習網頁 App

## 問題陳述

使用者的長期目標是英文聽說讀寫都進步到能進外商的程度，短期先加強讀與聽。他每天有兩段可用時間：通勤與走路時（只有耳機、單手操作、可能沒訊號），以及工作空檔（5-10 分鐘、清醒但零碎）。

現成的學習 app 內容不貼合他的程度與領域，也無法指定材料。而自己找材料練習的流程會斷掉——因為每次打開都要先決定「今天練什麼」，這個決策成本足以讓五分鐘的空檔被滑掉。

## 解決方案

一個托管在 GitHub Pages 的網頁，手機與電腦都用瀏覽器打開，可加到主畫面。

打開後**直接顯示今天該做的內容，沒有選單**。內容分兩種模式：閱讀模式（文字為主，適合坐著）與聽力模式（大按鈕、支援鎖屏控制，適合走路）。裝置類型決定預設模式，可手動切換。

內容由每日自動執行的管線寫入 Google Sheets（見 `2026-09-02-content-pipeline.md`），網頁透過 Google Apps Script 讀取，並在有網路時把近期幾天的內容與音檔快取到裝置，之後離線也能練。答題紀錄先寫進本機佇列，有網路時上傳到同一份 Sheets，手機與電腦因此共用同一份進度。

## User Stories

1. 身為使用者，我想打開網頁就看到今天該練的內容，不必先選單元，以便五分鐘空檔不浪費在選擇上
2. 身為使用者，我想在通勤沒訊號時仍能聽音檔與答題，以便地下鐵或電梯不中斷練習
3. 身為使用者，我想在手機上單手完成整段聽力練習（播放、暫停、重聽、作答），以便走路時能操作
4. 身為使用者，我想在電腦上讀完文章後、晚上用手機接著複習同一批單字，以便進度不會因換裝置而分裂
5. 身為使用者，我想讓答錯的題目與不熟的單字在幾天後自動再出現，以便真正記住而不是看過就忘
6. 身為使用者，我想看到本週練了幾天、答對率多少，以便判斷自己有沒有在進步
7. 身為使用者，我想在材料太簡單或太難時讓系統自動調整難度，以便一直練在剛好吃力的線上
8. （例外流程）身為使用者，當同步失敗時我想練習仍能繼續、恢復連線後自動補傳，以便不因技術問題中斷
9. （例外流程）身為使用者，當手機與電腦有各自累積的進度時，我想兩邊的答題紀錄都被保留、一筆不丟
10. （例外流程）身為使用者，當今天的新內容還沒產生時，我想直接看到待複習的舊項目，以便不會打開一個空白畫面、也不必為此做任何補救動作
11. （例外流程）身為使用者，當音檔載入失敗時，我想仍能讀逐字稿完成該課，以便單一資源失效不會廢掉整課

## 實作決策

**純靜態網站，無建置步驟。** 不使用需要 npm build 的框架。理由：使用者非工程師，任何需要編譯的流程在半年後會變成維護障礙——改一行字要先想起怎麼跑建置，通常結果就是不改了。改完直接推上去即可生效。

**內容與音檔都經 Apps Script 取得，repo 只放程式碼。** 內容存 Google Sheets、音檔存 Google Drive，網頁一律透過 Apps Script 這個單一入口讀取。理由：Drive 的公開檔案直連有 CORS 與配額限制，透過 Apps Script 代理則沒有跨網域問題，而 Apps Script 本來就要為了進度同步而存在——多一個 endpoint 的成本遠低於再引入一套供檔機制。

**離線用 Service Worker 快取最近 7 天的內容與音檔**，網頁以 PWA 形式加到主畫面。快取在有網路時預先抓取，不等使用者點開才抓——通勤時才發現沒快取就來不及了。

**當日內容可能尚未產生。** 生成管線每日早上執行，且允許「來源無合適內容」而跳過某天。網頁必須把「今天還沒有新內容」視為正常狀態，改為提供待複習項目，而非顯示錯誤。

**進度同步走 Google Apps Script + Google Sheets。** Apps Script 部署為 Web App，作為 Sheets 的讀寫介面，網頁直接對它發請求。無自建伺服器、無月費。

**Apps Script 存取控制**：部署為「任何人可存取」，但所有請求需在 query string 帶一個長隨機 token，Apps Script 端驗證後才回應。理由：設為「僅限本人」會強制 Google 登入，跨裝置摩擦大；而本專案資料僅為個人答題紀錄，無個資與敏感資訊，token 的強度足夠。token 以 `{SYNC_TOKEN}` 佔位，不進版控。

**答題紀錄採 append-only，不覆蓋。** 每次作答新增一列，主鍵為 `record_id`。複習狀態（某個單字下次何時出現）由紀錄推導而得，不另外存一份可變狀態。這是本設計的關鍵取捨：它讓兩台裝置各自離線累積後再上傳時**天然不會互相覆蓋**，代價是每次啟動要重算一次狀態——資料量在單人尺度下（一年約兩萬列）完全可負擔。

**離線佇列**：作答先寫入本機佇列，連線時整批上傳，伺服器確認後才清除佇列。每筆帶 `record_id`，重複上傳同一筆不會產生重複列（以 record_id 去重）。

**複習排程用 SM-2 的簡化版**：答對延長間隔（1 天 → 3 天 → 7 天 → 14 天 → 30 天），答錯重置回 1 天。不做完整 SM-2 的難度係數計算——單人使用看不出差異，多出來的參數只會讓行為難以解釋。

**難度調整**：以最近 20 題的滾動答對率為準，高於 85% 升一級、低於 60% 降一級，中間不動。級距用 CEFR，起始 B1。使用者未考過檢定、沒有既有基準；不做正式定位測驗（測驗要花 30 分鐘，測完仍要靠實際答對率調整，不如直接開始練）。

**難度必須回寫到 Sheets 的 `settings` 分頁**，因為選材的是 Spark，它每天讀那一格決定要挑多難的文章。網頁算出新等級卻不回寫，難度就會永遠停在 B1——這條回寫路徑是自適應機制的閉環，也是最容易被漏掉的一環。回寫時機為等級實際變動時，不是每次作答都寫。

**Apps Script API 契約**

| 方法 | 參數 | 回傳 |
|---|---|---|
| GET | `token`, `action=lessons`, 選填 `since`（`lesson_id` 日期） | 該日期之後的課程列，已解析為 lesson 物件；損壞的列以錯誤標記回傳而非略過 |
| GET | `token`, `action=audio`, `file_id` | Drive 中的 MP3 二進位內容（由 Apps Script 代理，避免跨網域問題） |
| GET | `token`, `action=progress`, 選填 `since`（ISO8601） | 該時間之後的所有答題紀錄陣列 |
| POST | `token`, `action=append`，body 為答題紀錄陣列 | 實際寫入的 `record_id` 清單 |
| POST | `token`, `action=set_level`，body 為 `{level}` | 寫入 `settings!B1`，回傳寫入後的值 |

**Sheets schema**：一列 = 一次作答

`record_id`（UUID）, `item_id`, `item_type`（`reading_q` / `listening_q` / `vocab`）, `lesson_id`, `answered_at`（ISO8601 UTC）, `correct`（boolean）, `device`, `client_version`

**內容 schema 與批次管線共用同一份定義**（見 `2026-09-02-content-pipeline.md`），避免兩邊各自漂移。

## 測試決策

**Seam（已與使用者確認）**：測試放在純函式層，不測畫面。畫面對不對使用者一眼就看得出來，而畫面測試在單人專案裡的維護成本高於價值。

| Seam | 簽章 | 要驗什麼 |
|---|---|---|
| 複習排程 | `scheduleNext(records, now) -> dueItems[]` | 給定答題紀錄與時間，算出當下該複習的項目。答對延長、答錯重置、未曾練過的項目優先 |
| 難度調整 | `adjustLevel(records, currentLevel) -> newLevel` | 滾動答對率的升降級判定，含樣本不足 20 題時不調整 |
| 同步合併 | `mergeProgress(localQueue, remoteRecords) -> {toUpload, merged}` | **一筆不丟**、重複上傳不產生重複列、兩裝置各自離線後合併結果與上傳順序無關 |
| 列解析 | `parseLessonRow(row) -> {lesson \| null, errors[]}` | 把 Sheets 原始列轉成 lesson 物件。**一列壞掉不能讓整批爆掉**——生成端是語言模型，JSON 格式不保證合法 |
| 內容驗證 | `validateLesson(lesson) -> errors[]` | 與生成管線共用同一支驗證器 |

**什麼算好測試**：只餵資料、只驗回傳值。不碰 DOM、不碰網路、不碰 localStorage——這些一律以參數傳入，讓上述四個函式保持純函式。

`mergeProgress` 是最需要測試的一個，因為它的失敗模式是「靜默丟掉幾筆進度」，使用者要幾週後才會察覺。這一項應涵蓋：兩裝置離線後同時上傳、上傳中途斷線、同一筆重送三次。

專案為全新建置，無既有測試慣例。測試工具選用交由下游計畫決定，但需符合「不引入建置步驟」的約束。

## 不在範圍

- **寫作與口說功能**：使用者已明確決定擺到第二階段。原因是他選定的兩個使用情境（通勤、工作空檔）都不方便打字或出聲
- **即時 AI 互動**（隨時提問、當場批改）：內容由 Gemini Spark 每日預先生成，網頁本身不呼叫 AI。這是為了用既有訂閱額度而非另付 API 費用的必然取捨，也是離線可用的前提。使用者已選擇「先批次，之後再加 API」
- **帳號系統與多使用者**：只有本人使用
- **上架 App Store**：網頁加到主畫面即可
- **正式程度定位測驗**：改用自適應難度
- **發音評分**：屬口說範疇，第二階段
- **真實新聞 / 商業 Podcast 內容**：見批次管線 spec
