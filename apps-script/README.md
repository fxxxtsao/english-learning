# Apps Script 部署與設定指南

這份文件說明如何設定專案後端的 Google Apps Script 環境。

## 檔案職責說明
在 Apps Script 專案中，主要由三個檔案負責不同的工作。
`Shared.gs` 是負責定義資料格式與驗證邏輯的核心，它與前端網頁共用同一套標準。
`Code.gs` 是負責與前端網頁溝通的橋樑，它會接收網頁的請求、驗證同步權杖，並將學習進度與新教材讀寫到試算表中。
`AudioFetcher.gs` 則是負責背景作業的輔助程式，它會每天自動去下載缺少的音檔，並每週清理過期的舊音檔以節省雲端硬碟空間。

## 貼上的順序
建議先建立並貼上 `Shared.gs` 的內容，再依序建立並貼上 `Code.gs` 與 `AudioFetcher.gs`。這裡要澄清一點：單純建立檔案、貼上程式碼並存檔，並不會馬上檢查其他檔案是否存在，所以先貼 `Code.gs` 也不會讓存檔動作立刻報錯。真正的風險發生在執行階段——只要 `setupSheets`、`generateToken` 這類函式被執行，或是網頁送出請求觸發 `Code.gs` 的邏輯時，只要 `Shared.gs` 還沒建立好，就會因為找不到 `parseLessonRow` 或 `Contract` 而報錯。因此請確保三個檔案都貼齊之後，再開始執行下面「手動執行的函式」，先貼 `Shared.gs` 只是最不容易出錯的順序，不是唯一可行的順序。

## 手動執行的函式
三個檔案都貼上後，有幾個函式只需要在首次設定時手動執行一次。

請在編輯器中選擇 `setupSheets` 函式並執行。這個動作會自動在你的試算表中建立所需的標題列與分頁，不會覆蓋已有的資料。
接著請選擇 `generateToken` 函式並執行。這個動作會產生一組全新的同步權杖並記錄在系統中，你必須將印出的字串妥善保留以供網頁連線使用。**注意**：如果之後又重新執行一次 `generateToken`，會產生「另一組」新權杖並覆蓋掉舊的，屆時所有已經連線過的裝置（手機、電腦）都會開始收到連線失敗的訊息，必須到每一台裝置上用新權杖重新設定一次。所以除非真的要更換權杖（例如懷疑外洩），否則不要重複執行這個函式。

**權杖不要寫在這個檔案裡。** 這份文件會進版控、會被推上 GitHub，寫在這裡等於公開。請把它記在專案根目錄的 `MY-SETUP.local.md`（該檔已設定為不進版控），或你自己的密碼管理工具。

最後請選擇 `installTriggers` 函式並執行。這個動作會向系統註冊時間排程，確保下載音檔與清理檔案的背景工作能按時啟動。這個函式可以重複執行：它每次執行都會先清掉舊的排程再建立新的，不會疊加出重複的排程。

## 部署為網頁應用程式（取得 exec 網址）
三個檔案貼齊之後，網頁前端要能連上這個 Apps Script，還需要把它「部署」成網頁應用程式，光是貼程式碼與存檔並不會產生對外的網址。

在編輯器右上角點「部署」（Deploy）按鈕，選擇「新增部署作業」（New deployment）。點設定區的齒輪圖示，選擇類型「網頁應用程式」（Web app）。「執行身分」（Execute as）請選「我」（Me，也就是你自己的帳號），「具有存取權的使用者」（Who has access）請選「所有人」（Anyone）——這兩項如果選錯，網頁會連不上或要求你的 Google 帳號登入，而不是用同步權杖驗證。點下方的「部署」後，第一次會跳出一個要求你授權的畫面，列出這個程式碼要存取你的試算表和雲端硬碟等權限，這是正常流程，同意即可。完成後畫面會顯示一個以 `https://script.google.com/.../exec` 結尾的網址，這就是要貼進手機與電腦網頁設定畫面的 Apps Script 網址，格式長得像 `https://script.google.com/macros/s/<一長串英數字>/exec`。同樣不要把真實網址寫進這份文件，記到 `MY-SETUP.local.md` 去。

**重要**：這個 exec 網址背後對應的是「部署當下」的程式碼快照，之後如果你在編輯器裡修改並存檔 `Shared.gs`、`Code.gs` 或 `AudioFetcher.gs`，這個網址預設不會自動套用新內容。要讓它生效，必須回到「部署」>「管理部署作業」（Manage deployments），點現有部署作業旁的鉛筆（編輯）圖示，把「版本」（Version）改選為「新版本」（New version），再按一次「部署」——網址本身不會變，但背後執行的程式碼會更新成最新版本。這個限制只影響網頁走的這條路徑；`fetchPendingAudio`、`cleanupOldAudio` 這類由時間觸發器啟動的背景工作，每次執行本來就會直接使用編輯器裡最新存檔的程式碼，不需要重新部署。

## 指令碼屬性 (Script Properties)
系統會在背景使用幾個重要的屬性來儲存狀態。

`SYNC_TOKEN` 是用來阻擋未經授權存取的密碼，網頁發送的每個請求都必須帶有與此屬性完全相同的字串。
`SPREADSHEET_ID` 是試算表的唯一識別碼，只有當你的 Apps Script 不是直接綁定在該試算表時，才需要手動加入這個屬性讓程式知道要去哪裡讀取資料。
`AUDIO_FOLDER_ID` 是儲存音檔的雲端硬碟資料夾編號，程式第一次下載音檔時會自動建立資料夾並將編號記錄在這裡。
`AUDIO_FETCH_FAILURES` 是用來記錄「每一課」音檔下載連續失敗的次數（依 `lesson_id` 分別計算，不是全站單一總數），當同一課連續失敗超過上限後，系統會透過這個紀錄決定不再自動重試，並寄一封 email 通知你。

## 觸發器的時間設定
預設情況下，音檔下載任務會在每天早上八點執行，而舊音檔清理任務會在每週日凌晨三點執行。這個早上八點是假設你在 Gemini Spark 設定的每日排程是早上七點左右執行，抓音檔的時間才特意晚一小時起跑。你必須明確對照你在 Gemini Spark 實際設定的執行時間來調整 `AudioFetcher.gs` 裡面 `FETCH_HOUR`（音檔下載）與 `CLEANUP_HOUR`（清理舊檔）這兩個設定值。音檔下載任務必須確保在 Spark 產生完文章之後才執行，否則會抓不到當天的內容——如果 Spark 的排程時間跟這裡的假設不一樣，請照實際時間修改後存檔，再重新執行一次 `installTriggers`（可安全重複執行，見上一節）讓新的時間生效。

## 關於 cleanupOldAudio 的設定
負責刪除舊音檔的 `cleanupOldAudio` 函式內部有一個名為 `DRY_RUN` 的安全開關，預設值為 `true`。在這個狀態下，程式只會在記錄檔中印出它打算刪除哪些檔案，而不會真的把檔案移到垃圾桶。當你確認記錄檔中的刪除名單準確無誤後，請回到程式碼中將 `DRY_RUN` 改為 `false`，這會讓系統在未來的排程中實際執行刪除動作。
